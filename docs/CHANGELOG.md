# dsh-corner-anim 🎬

**DSH 右上角的透明动画挂件：随 DSH 打开自动播放一次，播完停在最后一帧，
并把这一帧拆成「左电饭煲 / 右小女孩」两块各自可以拖着走的部分 ——
第一段播完之后，小女孩那块按两条节拍轮流播放待机动画（每 5 秒）与动作动画
（每 15 秒），**每段播完都停在她自己的末帧**，**屏幕上任何时刻有且仅有一段画面**，
控件（含**动画间隔调整**）跟着小女孩走。**

不新开窗口、不装第二套运行时、不占用额外端口 —— 一个纯 DSH 插件：
宿主半区把客户端脚本注入页面，客户端脚本只碰自己那棵 DOM 子树。

> **0.10.2 修复（四处，全部真浏览器实测复现 → 修复 → 断言）**
>
> 1. **播放待机 / 动作动画时，小女孩的身子被 DSH 窗口边框切掉一条。**
>    "贴住窗口右边缘"的间隙写死 2px，是按"动画内容比裁切框左右各宽 1~2px"量
>    出来的 —— 但这个溢出**随显示宽度线性放大**（溢出 = (内容宽×缩放 − 块宽)/2，
>    缩放跟着块走）。实测默认 220px 时刚好擦边，调到 300px 起内容右沿就越过
>    窗口右边框 1~11px（动作动画最宽）。现在 `girlSideGap()` 按所有动画层
>    （待机 / 动作 / 拖动 / 跑出 / 她那段，外加摞着的盆）的**实际溢出**现算间隙，
>    素材量出内容框时自动收紧一次 —— 任何宽度下她的主体都完整落在窗口里。
> 2. **拖「显示大小」滑杆时设置面板一路跟着跑，滑杆从光标底下溜走。**
>    滑块的每一次 input 都会让挂件块变宽变高（贴边 + 绕中心缩放），面板被
>    `layoutPanel()` 一路重摆（实测一次 80→600→120 的扫动面板上下追逐 202px）。
>    现在指针按在面板上的整个手势期间面板被**锚定在按下那一刻的视口位置**
>    （`panelLocked` + `panelAnchor`，块动多少就抵消多少），松手后再摆一次到位。
> 3. **开盖动画的触发条件改为「一轮对话完整结束」**，与
>    [DeepSeek-Balance-Whale-Widget](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget)
>    弹「本次消费金额」泡泡**同一触发点**：宿主监听 `session/event` 的
>    `turn/end` 把 `seq` +1，客户端每秒轮询 `GET /dsh-corner-anim/turn.json`，
>    `seq` 变大即触发（首个读数只对齐、不触发旧轮次）。旧"正文增长"探测
>    保留为兜底：信号连续 3 秒不可达才退回去。开盖结束后计时器照旧收掉
>    （0.7.4）；**点击停在最后一帧的开盖画面**（整格可点，含与锅块重叠的
>    区域）则把整条发送联动复位回「电饭煲 / 小女孩」各自独立可拖的拆分态，
>    两条待机节拍接回去。
> 4. **开盖停在末帧时点「重播动画」，冻结帧留在屏幕上赶不走、相位卡死、
>    控制条飞出视口右下角近千像素。** 重播的 `merge()` 不复位发送联动：
>    冻结帧挂在 body 上摘块清不掉；`sendPhase` 卡在 `'lid'`（锅不再接受
>    点击 Q 弹 / 随机动画）；搬走的控制条带着 `dshca-detached`（position:fixed）
>    + 旧视口内联回到带 `filter` 的宿主里被二次平移（实测渲染在 x=2419 /
>    视口 1440）。现在 `merge()` 先走一遍 `resetSendFlow()`，`split()` 里再
>    防御性归位一次控制条；顺带修掉"还原后排期不重启"（`paused` 标志未复位）。

> **0.10.1 修复（动画2 的两处，都是实测报出来的）**
>
> 1. **电饭煲没真的飞过去。** `applyFlight()` 一直把位移写进 CSS 变量
>    `--dshca-fly-x/y`，JS 侧的逐帧接触判定也在照常推进（自检里 `fly` 数值
>    一直在涨）—— 但 `.dshca-flying` 那条 CSS 里只有 `transition` 与
>    `will-change`，**从来没有声明 `transform` 去消费这两个变量**。变量写了
>    没人读，锅在画面上就纹丝不动。现在补上了
>    `transform: translate(var(--dshca-fly-x,0px), var(--dshca-fly-y,0px))`，
>    并且真浏览器断言到**计算样式**那一层：飞行中 `transform` 是非 `none` 的
>    matrix、接触复位后回到 `none`。
> 2. **她头上摞着盆时触发动画2，盆浮在坐姿动画的半空。** `openGirlBasinFlow()`
>    起播她那段时让她的定格 canvas 让位了，却漏了盆的让位 —— 盆的
>    `refreshPotsVisible()` 只挂在 girl.webm / 拖动动画那两条路径上。现在
>    动画2 的整条生命周期都收口了：她那段出画时盆让位、她那段收工
>    （接触复位 / 5 秒兜底 / 重播 / 关闭 / 新一轮发送）时盆原样回来。

> **0.10.0 新增：拖动动画 + 电饭煲的两种随机动画**
>
> **① 拖小女孩时，她会被"拎起来"**
>
> 拖**小女孩那一块**（真越过 3px 的拖动阈值，不是按住不动）时循环播放
> [assets/drag.webm](dsh-corner-anim/assets/drag.webm)（5.542s），**松手立刻切回**
> 她原来那一格 —— 用户明确选的是"立刻切回"，所以没有做 VPet 那种 C_End 收尾动作。
> 拖动期间她头上的盆会一起让位（那段素材自己画着"被拎起来"的样子，浮在半空的盆会穿帮）。
> 参考的是 VPet 的拖动状态机（`Raised_Dynamic` → 静态，见
> [`vpet-drag-logic/`](../vpet-drag-logic)）：那边是"拖动时播动态帧、松手走收尾"，
> 这里用一段循环素材对应"动态"这一半。想关掉用配置 `dragAnim: false`。
>
> **② 点电饭煲，先掷两个互斥的骰子**（一次点击**最多**触发一件事）
>
> | 结果 | 概率 | 会发生什么 |
> | --- | --- | --- |
> | 动画1「开盖 · 空锅」 | `randomAChance`，默认 **20%** | 播 [lid-empty.webm](dsh-corner-anim/assets/lid-empty.webm)（带原始音轨）→ 正常播完后**倒放**回第 0 帧 → 倒放一结束立刻把画面交回电饭煲原来那格定格图 |
> | 动画2「开盖 · 米饭热气」 | `randomBChance`，默认 **10%** | 两边**同时**开始：小女孩那块演 [girl-basin.webm](dsh-corner-anim/assets/girl-basin.webm)（钢盆扣在头上、左右张望），电饭煲在 **5 秒**内沿直线向她移动；两块矩形**真的相交**那一刻双方立刻复位 |
> | 什么都没掷中 | 默认 **70%** | 完全回到 0.8.0 的行为：点击 Q 弹 + 按压音效 |
>
> 两个概率是**互斥**的，不是各掷一次：先问 A，只有 A 没中才问 B —— 所以
> "点一下会演点什么"的总概率正好是两者之和，而两者永远不会同时播。
> 掷中随机动画的那一次**不响按压音**（那两段素材本来就带声音），也不压扁。
>
> **③ 动画2 的"接触"是逐帧判定的**
>
> 移动量不是一格一格挪出来的，而是**一次算清**：在"原位 → 她的位置"这条直线上
> 按比例采样 160 个点，用她那块的矩形求每个点的重叠率，取最大的那个当终点
> （终点不越过接触点 —— 越过了只是白穿过去）。然后逐帧（`requestAnimationFrame`）
> 把进度推上去，**哪一帧两块矩形真的相交过半（≥50% 面积比）就算接触**：
> 那一刻电饭煲立刻归位、"移动"用的 `transform` 与 class 全部清掉，她那段收工，
> 两边都回到各自的定格图，两条动效节拍接着照常跑。
>
> 判定用的是**她那块里的那张贴片**（她那两段素材里内容会漂，所以取"整段贴片包围盒"
> 与"当前这一帧的矩形"的**交集**）—— 宁可判得稍晚，也不会"锅还离得老远就算碰到了"。
> 5 秒没碰到（比如她自己被拖到了屏幕另一头）也算"已经贴上了"，照样收工，不会永远挂着。
>
> **④ 顺手修掉的三处老毛病**（都是这次在真浏览器里量出来的）
>
> 1. **动画2 点出来却只有锅在开盖。** 掷中 B 的那条分支直接调了
>    `playRandomLid('lid2')` —— 那只换电饭煲那一侧的画面，"她那段 + 追过去"
>    整套编排全都没启动。现在 B 走 `openGirlBasinFlow()`。
> 2. **一按下拖动她会闪一下不见**（100~150ms）。根因是"先收她的图、再等拖动动画
>    第一帧就绪"：中间那一段屏幕上什么都没有，而且 `playing` 迟到时那一步还会
>    落到"拖动已经结束"之后（于是拖动动画留在屏幕上不走）。现在改为
>    **先让拖动动画占位、再收她的图**，并且 `stopDragAnim()` 做成幂等的
>    （不管标志是什么，都把层收干净）。
> 3. **开启动画1 时她整个人凭空消失 5 秒** —— 因为一度把"随机动画在演"也当成了
>    "她该让位"。电饭煲开自己的盖跟她本来毫无关系，现在她那一侧照旧。
>
> 想整体关掉用 `randomAnims: false`（或把两个概率都设 0）；
> 想在控制台手动演一遍用 `window.__dshcaRandom.play('lid1'|'lid2')` /
> `.drag(true|false)` —— 这两个入口**不受概率限制**，验"那 20%"就靠它们。

> **0.9.0 新增：掉盆（点小女孩的随机事件）**
>
> 按压**小女孩**时额外掷一个骰子（`potChance`，默认 **10%**）：掷中就让一个倒扣的
> 钢盆**从天而降**、扣在她头上 —— 盆沿碰到头顶那一刻响一声「钢盆」（`basin.mp3`），
> 同时"哐"地压一下再弹回。压扁与按压音照旧，两件事互不影响。
>
> 几个能玩的地方：
>
> - **可以一直摞**：每多一个盆就往上抬高一点，还带一点随机的水平偏移与倾角 ——
>   不会像复制粘贴；
> - **拖她的时候盆跟着走**（盆是她那一块的子节点），改显示尺寸也一起缩放；
> - **拖到一旁就能摘掉**（离原位够远就消失，上面的重新摞下来）；拖一点点则弹回原位；
> - 重播 / 关闭会把盆全部收掉。
>
> 盆是**独立于画面的硬家伙**：它不被"点击 Q 弹"拍进快照、也不会跟着压扁，而且
> 悬浮按钮仍压在它上面（叠放层级：画面 < 盆 < 控制条）。
> 想关掉用配置 `potChance: 0`。
>
> 同一次交付还把**「钢管」彩蛋音调小了一半**（`pipeVolume: 0.5`，作用在
> `pressVolume` 之上）—— 普通按压的合成音音量不变。

> **0.8.0 新增：点击 Q 弹（按住压扁 / 松开弹回）**
>
> 拆分后的**电饭煲**与**小女孩**各自可以按住：按下那一刻先**暂停**当前这一段，
> 把「它当时所在的那一帧」拍成一张快照并**压扁**（`scaleY .88 / scaleX 1.05`，
> 支点在底部中线 —— 锅的底座、她的脚不动），松开时用一条带回弹的缓动弹回原状，
> 然后**从暂停处继续播放**。按下时本来就没在播的（还没起播的定格帧、已播完停在
> 末帧的那一格、被 ⏸ 冻住的那一格）就只把画面放回去，不接播放。
>
> 手感与 `dsh-whale-widget` 的按压 Q 弹一致（同一组形变参数与同一条缓动曲线）。
> 两条刻意划出的边界：**只对拆分后的两块生效**（合并态的开场动画不参与）；
> **发送联动的两段动画**（`girl.webm` 跑出、`lid.webm` 开盖）播放期间**自动让开**
> —— 那两段有自己的时序（演完要搬按钮、收计时器），点按不该把它们按住。
> 想整体关掉用配置 `clickSquish: false`。
>
> 顺带一条容易踩空的地方：按住期间**排期器会把这一拍让过去**（像"正在播的不打断"
> 那样往后挪一拍），否则松手时露出来的会是一段已经跳过去的动画。
>
> **按压音效**（同一次交付）：普通按压响一声**现场合成**的短促"软弹"（不要素材）；
> 而**按压电饭煲**时有 **7%** 的概率改响随包的 `assets/pipe.mp3`（"钢管"，开头
> 2.84 秒的静音已按 MP3 帧边界**无损**裁掉）。两者共用一套**内置 CD**：
> **上一个音没播完就不出声**，再叠 150ms 的最小间隔防抖 —— 所以连点**永远不会叠音**，
> 而且被 CD 吃掉的那次按压**不会消耗掉它那 7% 的机会**（先判 CD、再掷骰子）。
> 开关 / 音量 / 概率见配置 `pressSound` / `pressVolume` / `pipeChance`；
> 想在控制台试听用 `window.__dshcaPress.play('pipe')`。

> **0.7.5 调整（你要求的一条）**
>
> **开盖动画改为等「深度思索」结束之后再播；思索期间电饭煲保持原样**（既不播开盖，
> 也不藏锅）。判据不再只看"页面上有文本在变长"—— 思索期间在变的除了推理预览，还有
> 「正在分析请求 / 正在读取文件 / 正在调用工具」这类**过程行**（它们不在推理行里，
> 任何按文本长度做的排除都排不掉），所以旧判据会在模型还没想完时就成立。
>
> 现在直接读 DSH 自己的推理行（`@deepseek-ai/dsh-client-ui-chat` 的 `ReasoningRow`）：
> `<div data-variant="think" data-state={running ? 'running' : 'ok'}>` —— **data 属性、
> 与构建哈希无关**。`data-state="running"` 时一律按住不播；它一想完，同一条判据
> 立刻再次成立、开盖紧接着就播。按住期间**一个字的状态都不改**（基线 / 峰值 / 静默
> 时刻全不动），所以时机不会因此变晚。
> 顺带两条：思索期间不再因为"等得太久"而放弃这一轮（观测器的 10 分钟超时会在思索中
> 顺延）；`window.__dshcaSend.probe()` 多两个字段 `reasoningRunning` / `heldForReasoning`，
> `debug()` 里多了 `output-held-reasoning` / `reasoning-ended` 两笔。

> **0.7.4 调整（你要求的一条）**
>
> **开盖动画播完 → 蓝色文案「肥鱼已经煮饭：」与计时器一起收掉**，开盖画面**仍停在
> 最后一帧**。计时器不只是被藏起来：那条"每秒读一次表 + 重排一次发送列"的
> `setInterval` 也一并停掉，免得在没人看得见之后还空转。
> 下一条消息复位时，文案与计时器会重新出现并从 `00:00` 开始走。
> 判据带一个相位守卫：只有仍处在 `lid` 相位的那次 `ended` 才算数，
> 迟到的 `ended` 不会把新一轮的计时器收掉。

> **0.7.3 修复（你实测报的三条）**
>
> 1. **开场动画播完后，小女孩悬在离窗口边框 40~50px 的地方。** 素材画幅右侧本来就有
>    320 源像素（2560 的 12.5%）的透明留白，照搬"她在帧内的位置"就等于把她停在窗口
>    内侧。现在拆分时**只把她一个人顶到窗口右边缘**（留 2px 细缝，免得待机/动作动画
>    那 1~2px 的溢出被边缘切掉），并且整块完整落在窗口内 —— 电饭煲仍停在帧内的位置。
>    改窗口大小、改显示尺寸都会重新贴边；**你自己拖动过她之后就不再自动贴边**。
>    顺带修掉一个相关的老毛病：两块的位置以前要"都存在"才生效，于是**只拖过小女孩**
>    的那次拖动会被忽略；现在两块各自判断，只摆过一块也照样记住。
> 2. **播放跑出动画时，"原先那张她"还留在屏幕上。** 她那段素材大部分是透明的，底下
>    只要还有东西亮着（拆分时裁出来的定格帧，或者待机/动作那一路停下的末帧），屏幕上
>    就会同时出现两个她 —— 看起来就像跑出动画没播。现在这一段**独占画面**：两路节拍
>    与她的定格 canvas 一起让位，演完再把画面交回去。
>    顺带修掉一个同源 bug：重播会先摘掉两块（连同她那段视频），而视频节点是留着重用的
>    —— 于是第二轮她"演"的是一段已经不在页面里的视频。现在挂载前会确认它还挂在右块上。
> 3. **开盖动画播在了计时器下方。** 它原来挂在"文案 + 计时器"那一列里，所以只能出现在
>    计时器下面。现在它是**原地盖在电饭煲位置上**的一层（内容下沿对齐锅的下沿、水平
>    对着锅的中线），文案与计时器仍留在电饭煲正下方 —— 于是开盖看起来就是那口锅自己
>    在开盖，屏幕上始终只有一口锅。

> **0.7.2 修复（你实测报的三条）**
>
> 1. **思考很短时开盖不播、计时器却一直走。** 原来"观察输出"是**小女孩演完之后**
>    （约 5 秒）才架起来的。若这轮"思考 + 输出"在 5 秒内就跑完，等架子架好时正文
>    **已经写完、不再变长**，增长判据永远不成立 → 开盖不播、计时器照走。
>    现在改成**点发送那一刻**就取基线（复位是同步的，所以顺序是"先复位、再观察"），
>    输出发生在她还在演的时候也照样抓得到，并**记下来等她演完立刻补播**。
>    同时把增长阈值从 24 字降到 2 字，并新增一条**静默判据**（正文有过变化、
>    之后连续 1.2 秒没再变，就算输出开始了）—— "只回一句短话"的回答可能永远
>    长不到阈值那么多字。
> 2. **思考期间就播了开盖。** 两条成因一起修：① 实机"思考"那一行的推理内容
>    **也是流式文本**，兜底判据（全页文本）把推理算成了正文 → 现在兜底路径也
>    **显式排除**推理行（既按类名前缀 `_3GBCTG_` 认，也按标题"思考"认，双保险）；
>    ② 新增的静默判据一开始过于激进，会在"正文还是空的"时候判定"静下来了"
>    → 现在要求**必须真的长过一点**才允许走静默那条路。
> 3. **屏幕上出现两口锅。** 开盖那段素材里本来就画着一口完整的锅（从合盖到开盖），
>    所以它播放期间原来那块电饭煲定格图必须让位 —— 否则视频里的锅与裁出来的锅
>    会同时出现。现在开盖期间给那一块加 `dshca-cooker-hidden`
>    （只藏画面，用 `visibility` 而不是 `display`，盒子/布局/拖动都不变），
>    于是**无论何时屏幕上只有一口电饭煲**。
>
> 顺带修掉一个相关可用性问题：原来"重新允许发送"只靠一个 1.5 秒定时器，
> 而一轮回答可能跑几分钟，下一条消息点发送时会被它吃掉。现在改成
> "**短窗口去抖** + **一轮收尾后立刻重新武装**"两条一起用。

> **0.7.1 修复（拿到实机 DOM 之后改的两条）**
>
> 1. **"开始输出"的判据原来会提前命中**：DSH 每轮都会挂一行「思考」，
>    而那一行里的推理内容**本身就是流式文本** —— 原来的判据是"全页文本在变长"，
>    于是模型还在思考时开盖动画就播了。现在改成只看**回答正文容器**
>    （`[class*="_markdown_"]`，并排除 `_3GBCTG_` 那行"思考"）。
>    顺带修掉一个更隐蔽的逻辑错：原来用 `sendLastText === 0` 表示"还没取基线"，
>    可一轮刚开始时正文确实是 0 个字 —— 那 0 是合法基线，于是"从零长出来的
>    第一条回答"永远触发不了。
> 2. **发送按钮改用实机上那个稳定的锚点**：`button[aria-label="发送消息"]`
>    （精确匹配优先，文案宽匹配兜底），输入框认 `role="textbox"` /
>    `contenteditable` / aria 里带"发消息"。实机这一版**没有"停止生成"按钮**，
>    所以回车那条判据只依赖"存在一颗可用的发送按钮"。

> **0.7.0 新增：和「发送消息」联动**
>
> 侦测到你点了「发送消息」（或在输入框里回车）之后，按顺序发生两件事：
>
> **事件 1** —— 右侧小女孩那块上面播 [assets/girl.webm](dsh-corner-anim/assets/girl.webm)
> （1920×1080，单次不循环）；她演完的那一刻：控制条那五颗按钮**搬到电饭煲上方**、
> **小女孩本人隐藏**，电饭煲下方出现蓝色文案「肥鱼已经煮饭：」与一个**计时器**
> （从这一刻开始按 `mm:ss` 走）。
>
> **事件 2** —— 模型思考结束、**开始输出结果**时，在计时器下方播
> [assets/lid.webm](dsh-corner-anim/assets/lid.webm)（2560×1440，**带声音** ——
> 按你的要求没有抽掉音轨），播完**停在最后一帧**。
>
> 再发一条消息 → 整套重置重来（小女孩回到原位、按钮回到她那一侧、计时器归零）。

> 两处侦测都靠观察 DOM（页面脚本读不到 React 状态），判据刻意与 class 名无关，
> 分别是"命中发送语义的按钮被点/回车"与"页面文本总长在增长"；
> 想指定按钮用 `sendSelector`，想关掉整个联动用 `sendHook: false`。
> 详见下面「和发送消息联动」一节。

> **0.6.0 变更（两条）**
>
> 1. **动画间隔可调**：控制条上新增一颗 `⇄1×` 档位按钮（点击在 0.5× / 1× / 2× / 4×
>    之间循环），设置面板里新增一条「动画间隔」滑杆（对数刻度 0.25× ~ 4×）做精细调整。
>    倍率是**乘法**，两条节拍同比缩放（5s/15s 在 2× 下就是 10s/30s）；正在播的那段
>    不被打断，改完两条节拍一起从当下重新起算。调过的值记在 `dsh-corner-anim:speed:v1`。
> 2. **停在动画结束的地方**：一段动画播完之后，画面**留在它自己的末帧上**，
>    不再把画面交还开场那张定格帧 —— 于是每次动画结束，小女孩都不会一跳回到
>    开场的姿势；空档期、暂停、继续之后同样是她自己的末帧，直到下一拍到点
>    换成新的动画。开场定格帧从此只在**首拍之前**出画。
>    （修的是一个一直存在的观感问题：旧实现有一个 200ms 的"收工"定时器，
>    到点就把播放层撤掉、露出下层定格帧。）

> **0.5.0 变更**：拆完两块之后，小女孩那块不再只是循环一段待机，而是
> **两段素材各自一条节拍轮流出画** —— `idle.webm` 每 5 秒起播一次、
> `act.webm` 每 15 秒起播一次；谁的表先到点谁上，两边同时到点则动作动画优先，
> 正在播的那段不被打断。
> 控制条上那颗 Debug 键改为**暂停 / 继续整条排期**（即原来的 ▶ 待机按钮）。
> 同时修掉了一个真 bug：**暂停时会把下层那张定格帧露出来**（画面从某个动作
> 一跳回到开场最后一帧）。现在暂停是"原样冻住"，见下面「暂停为什么不再露馅」。

> **0.5.1 修复**：按下「继续动画排期」之后，**其它动画再也没出现过**。
> 根因是暂停时冻住的那一格被继续沿用成"当前画面"：它既不会有 `ended`
> （永远不会自然收工），又被判成"正在播"占着屏幕，于是之后每一拍都被当成
> "已经有人在出画，跳过" —— 屏幕上永远只剩那张冻住的图。
> 现在把"谁在屏幕上"收成**唯一判据 `shownKind`**：每次状态变化都由
> `showOnly()` 重新决定。保证随之变成一条可断言的不变量：**任何时刻屏幕上恰好
> 一段画面**（一段动画或定格帧，不会两段、也不会空）。详见「屏幕上永远有且仅有一段画面」。

## 它做什么

| 行为 | 说明 |
| --- | --- |
| **打开 DSH 就播放** | 脚本随 DSH 页面一起加载，`<video>` 自身带 `autoplay`（且 `muted`，所以不会被浏览器自动播放策略拦下），每次打开 DSH 播放一次。 |
| **停在最后一帧** | **不设 `loop`** —— 不循环、不淡出、不移除。`ended` 时显式 `pause()`，画面就停在最后一帧。 |
| **播完拆成两块** | 在最后一帧里自动找出两个主体之间的透明缝隙，把**电饭煲**和**小女孩**各裁成一块，各自成为一个可独立拖动的部分。电饭煲留在它在帧里的位置；小女孩**贴到窗口右边缘**且整块完整可见（0.7.3，见下面「小女孩为什么贴在窗口边框上」）。 |
| **小女孩接着动起来** | 拆完就开始跑排期：**待机动画每 5 秒**、**动作动画每 15 秒**各起播一次，两段轮流出画；电饭煲仍停在最后一帧。节拍快慢可在控制条与设置面板里调（见「动画间隔」）。 |
| **同一时刻只有一段画面** | 两条节拍各自计时，但**屏幕上任何时刻有且仅有一段**：要么某一路动画（含它播完后的末帧），要么首拍之前那张定格帧。谁先到点谁上；两边同时到点（5s 与 15s 每 15 秒必撞一次）则**动作动画优先**；正在播的那段**不被打断**，错过的这一拍直接跳过。暂停 / 继续也不会破坏这条不变量。 |
| **停在动画结束的地方** | 一段动画播完就**停在它自己的末帧**（`<video>` 不设 `loop`，`ended` 之后引擎继续显示最后一帧），不会把画面交还给开场那张定格帧 —— 所以动画之间、暂停、继续之后，小女孩都还是她自己的姿势，不会一跳回到开场。 |
| **两段都是独立素材** | `assets/idle.webm`（1440×1920，VP9 + alpha，**已预先用 `-c copy -an` 抽掉音轨**）与 `assets/act.webm`（1440×1916，VP8 + alpha，**本身就是无声素材**）—— 挂件永远静音，也不会为听不到的 BGM 多传字节。 |
| **控件留在小女孩一侧** | 重播 / 排期 / 间隔 / 折叠 / 关闭五颗按钮与整个设置面板都挂在小女孩那块上；电饭煲那块不带任何控件，只有它自己。 |
| **拆分前可整体拖动** | 播放期间整块按住即可拖动，指针 1:1 跟手；位置写进 `localStorage`。 |
| **拆分后就地裂开** | 没被摆过时，电饭煲落在它在原图里的位置，所以它那一侧拆开前后**完全重合**；小女孩则被顶到窗口右边缘（0.7.3：素材画幅右侧那 320px 透明留白会让她离边框 40~50px，那段留白不该由她来承担），只有拖走才看得出是两块。 |
| **不会被拖丢** | 每一块都至少保留 56px 在视口内；改变窗口大小后自动重新夹紧；改大小后也会重新夹紧。 |
| **点击 Q 弹**（0.8.0） | 拆开后的电饭煲 / 小女孩**按住会被压扁**（底部不动、横向微胀），松开弹回原状。被拉伸的是**按下那一刻的那一帧**（按下即暂停并拍成快照），松手后**从暂停处继续播放**；本来没在播的就只放回画面。拖动与按压缩放是同一个手势的两面：按住不放再移动就是拖动，压扁着的画面跟着走。只对拆开后的两块生效，发送联动的两段动画期间自动让开。 |
| **按压音效**（0.8.0） | 每次按压响一声**现场合成**的短促"软弹"；**按压电饭煲**时另有 **7%** 概率改响 `assets/pipe.mp3`（"钢管"，音量是普通音的一半）。两者共用**内置 CD**：上一个没播完就不出声 + 150ms 防抖 —— 连点**永不叠音**。开关 / 音量 / 概率：`pressSound` / `pressVolume` / `pipeVolume` / `pipeChance`。 |
| **掉盆**（0.9.0） | 按压**小女孩**时 **10%** 概率从天而降一个钢盆扣在她头上，碰到头顶响一声「钢盆」；**可以一直往上摞**（每个略高一点、带随机偏移与倾角），**拖她时盆跟着走**，**拖到一旁就能摘掉**（上面的重新摞下来）。盆是独立于画面的硬家伙：不被拍进快照、不跟着压扁，控制条仍压在它上面。概率用 `potChance`（`0` = 关掉）。 |
| **拖动动画**（0.10.0） | 拖**小女孩那一块**时循环播放 `assets/drag.webm`（"被拎起来"那一段），**松手立刻切回**她原来那一格。真越过 3px 拖动阈值才起播（按住不动仍走点击那一套）；拖动期间她头上的盆一起让位。开关 `dragAnim`，大小 / 速度 `dragScale` / `dragRate`。 |
| **电饭煲的两种随机动画**（0.10.0） | 点击电饭煲时先掷两个**互斥**的骰子：**20%**（`randomAChance`）播动画1「开盖 · 空锅」`assets/lid-empty.webm`，播完**倒放**回原样、立刻交回定格图；**10%**（`randomBChance`）播动画2「开盖 · 米饭热气」`assets/lid-rice.webm` —— 小女孩那块同时演 `assets/girl-basin.webm`（钢盆扣头），电饭煲在 **5 秒**内沿直线向她移动，**两块矩形真的相交**那一刻双方立刻复位。两个都没中（默认 70%）才走点击 Q 弹 + 按压音。两段都**保留原始音轨**。详见下面「电饭煲的两种随机动画」。 |
| **透明背景** | 素材是带 alpha 通道的 WebM（`AlphaMode`），页面背景完全透出，没有任何底板。 |
| **不挡操作** | 宿主节点尺寸等于可见内容本身，除挂件区域外不拦截任何指针事件；设置面板不会误触发拖动。 |

悬浮在挂件上会出现五个小按钮，从左到右：

| 按钮 | 作用 |
| --- | --- |
| **↻ 重播** | 先把两块合回整体（动画层随之退场、排期作废），再从头播一遍；播完会重新就地拆开，然后重新开始排期并停在新动画的末帧。 |
| **⏸ 排期 / ▶ 继续** | **Debug 按键**：暂停 / 继续整条节拍。**暂停**只让节拍停摆、画面原样冻在当前这一帧（不撤层、不露定格帧，屏幕上仍是这一段）；**继续**从当下重新计时（不补播错过的拍），冻住的那一格继续留在屏幕上，下一拍到点被新动画接走。排期在跑时按钮点亮成蓝色（`aria-pressed="true"`）。两种状态下屏幕上始终只有一段画面。 |
| **⇄ 间隔** | 动画间隔档位：点一下切到下一档（0.5× → 1× → 2× → 4× → 回卷到 0.5×）。按钮上的数字就是当前倍率，悬停提示里写着它对应的实际节拍。见下面「动画间隔」。 |
| **▾ 折叠 / ▴ 收起** | 展开或收起下方的设置面板。面板展开时按钮与面板会保持常显，不用一直悬停。 |
| **✕ 关闭** | 本次运行内移除（刷新页面后会回来；想永久关掉见下面的配置）。 |

### 设置面板

展开后有两组控件。

**显示大小**：

- **滑杆** —— 拖到哪就是多大，宽度实时生效，高度按素材宽高比自动跟随；
- **小 / 中 / 大** —— 三个预设，分别是配置里 `width` 的 0.6× / 1× / 1.5×（默认即 132 / 220 / 330 px），当前值对应的那个会高亮；
- **重置** —— 清掉记住的尺寸与动画间隔，回到配置里的 `width` 与 1×。

**动画间隔**：

- **滑杆** —— 对数刻度 0.25× ~ 4×，**中点是 1×**，所以往左拖变快、往右拖变慢，两边手感对称；
- **0.5× / 1× / 2× / 4×** —— 四个档位预设，与控制条上那颗按钮改的是同一个值（点哪边都会同步）；
- 面板标题右侧的读数是**算完之后的实际节拍**，例如 `2×（待机 10s / 动作 30s）`。

改动会写进 `localStorage`：尺寸是 `dsh-corner-anim:size:v1`、动画间隔是
`dsh-corner-anim:speed:v1`，**下次打开 DSH 依然是你调过的值**；
面板的展开 / 收起状态同样会被记住（`dsh-corner-anim:panel:v1`）。

面板会自己找位置：默认贴在挂件下方、与挂件右缘对齐；下方放不下就翻到上方，
左右越界也会自动夹回视口内 —— 所以把挂件拖到屏幕任意角落都能正常用。

## 点击 Q 弹（0.8.0）

拆开之后，**电饭煲**和**小女孩**各自都是一个可以按住的玩偶。

| | 按下 | 松开 |
| --- | --- | --- |
| **画面** | 当前这一段被**暂停**，它当时所在的那一帧被拍成一张快照，快照**压扁**成 `scaleY .88 / scaleX 1.05`（支点在底部中线，所以锅的底座 / 她的脚不动） | 快照用一条带回弹的缓动弹回原状（`cubic-bezier(.34,1.56,.64,1)`，.22 秒），过渡走完才把快照收掉 |
| **播放** | 被按住的这一段**冻住**，按住多久就停多久 | **从暂停处继续播放**（需求里的"点击行为结束后，继续原先的视频播放行为"）；按下时本来就没在播的——还没起播的定格帧、已播完停在末帧的那一格、被 ⏸ 冻住的那一格——**只把画面放回去，不接播放**（"若无则不继续"） |
| **节拍** | 排期器把这一拍**让过去**（按原相位往后挪一拍，等价于"正在播的不打断"） | 回弹结束之后节拍照旧 |

被拉伸的**不是**一张固定素材，而是**按下那一刻它所显示的那一帧**：命令的顺序是
"先 `pause()` 冻住 → 再拍照 → 再压扁"，所以按住期间画面不会继续走动。

两条边界（都是刻意划的）：

- **只对拆开后的两块生效。** 合并态（开场动画还在演的那一整块）不参与 ——
  它本来就只有一块、也还没"拆成电饭煲和小女孩"。
- **发送联动的两段动画期间自动让开**：`girl.webm`（点发送后她跑出去那一段）
  正在演的时候按她不响应；`lid.webm`（模型开始输出时的开盖）盖在电饭煲位置上的
  期间按锅也不响应。这两段有自己的时序（演完要搬按钮、收计时器），点按不该把它们
  按住。**发送联动的复位会顺手把还在进行的那次按压收干净**（重播 / 关闭同理），
  所以不会出现"快照盖在开盖视频上面"。

几个实现上的取舍（都在 `assets/widget.js` 的「点击 Q 弹」一节里）：

- **快照是"与那一块等大的一张 canvas"**，画的时候按**内容包围盒**取源、并复算
  动画层那套"水平居中、底边对齐"—— 两处必须同源，否则按下的一瞬画面会跳一下。
  动画层与定格帧都带大片透明留白，直接按元素盒子取源会让支点落在留白里（压扁时
  人会往上飘几像素）。
- **快照挂在画面层之上、控制条之下**（`insertBefore(bar)`）：悬浮按钮仍然点得到，
  也不会跟着一起被压扁。
- **按下与拖动是同一个手势的两面**：`pointerdown` 立刻压扁（和鲸鱼挂件一样），
  位移超过 3px 就成了拖动 —— 压扁着的画面跟着走，松手时落地并弹回。
  **没有位移的按下不会写任何位置记忆**（它没有被当成拖动）。
- **强制一次样式刷新再改 class**：元素刚插进 DOM 就改 `transform`，浏览器没有可比的
  初始值，会"啪一下到位"而不是走过渡。真实浏览器实测踩到过这一条（DOM 桩里看不出来，
  所以另有一条 `test/cdp-squish.mjs` 在真浏览器里守着它）。
- **一份快照在"松手后回弹"期间还活着**：这 260ms 里如果发生重播 / 关闭 / 发送联动
  接管画面，那一次也会被立刻收干净（`squishSettling`），不会留下一个"永远不播的
  视频元素"或者孤儿快照。

### 按压音效

同一次按压还会出一声。两个音源，**一次按压只会响其中一个**：

| | 什么时候 | 声音 |
| --- | --- | --- |
| **普通按压** | 拆开后两块里的任何一次按压 | **现场合成**的短促"软弹"：三角波从 520Hz 快速滑到 170Hz，配一条指数衰减包络（约 0.17 秒）。不占素材、不占请求，音量直接乘 `pressVolume` |
| **钢管彩蛋** | **只在电饭煲那一侧**，且掷中 `pipeChance`（默认 **7%**） | 随包的 [assets/pipe.mp3](dsh-corner-anim/assets/pipe.mp3)（1920×1080 那套素材之外的**唯一一个音频素材**） |

**内置 CD**（两条判据合起来，"避免多个音效叠加播放"）：

1. **上一个音还没播完就不出声** —— 合成音占 0.17 秒，钢管音占它自己的 2.42 秒。
   一次按压就是一次按压：**整次静音**，不会有半声，也绝不会两个音重叠。
2. **距上一次"起播"不足 150ms 也不出声** —— 合成音太短，没有这条防抖就能被连点成
   机关枪。

还有一个刻意的顺序：**先判 CD、再掷骰子**。被 CD 吃掉的那一次按压不该消耗掉它那
7% 的机会，否则连点两下就等于把彩蛋概率翻倍。

实现上两个细节：

- **AudioContext 是惰性创建的**，触发点就是第一次按压 —— 那一刻正是用户手势，
  所以不会被自动播放策略拦下，也不会在页面加载时就建上下文（控制台的告警来源）。
  真的建不起来（老浏览器 / 被策略拦住）时**整条音效路径静默退场**，画面照旧。
- **`pipe.mp3` 在第一次按压时才 fetch + `decodeAudioData`**（不等于开页面就拉），
  解码好之前万一掷中彩蛋就先用合成音顶上；**素材 404 / 解码失败也只是没有彩蛋**，
  绝不让"点一下没有反应"。

控制台里可以试听与排查：

```js
window.__dshcaPress.probe()          // CD 还剩多久、素材就绪没有、上一次响的是哪种
window.__dshcaPress.play('pipe')     // 手动听一遍（不受 CD 限制）
window.__dshcaPress.play('synth')
window.__dshcaPress.reset()          // 清掉 CD
```

`assets/pipe.mp3` 由用户提供；原始文件开头有 **2.84 秒静音**，已用
[tools/audio-trim.mjs](dsh-corner-anim/tools/audio-trim.mjs) **按 MP3 帧边界无损裁掉**
（83949 → 39168 字节，剩 2.42 秒）。这台机器上没有 ffmpeg，所以那个工具用无头
浏览器解码量静音、再按帧切字节 —— **不重编码，音质不变**；顺带也解释了为什么
"裁静音"这件事不能用字节数算。

验证分两层，都是可复跑的：

```powershell
node test/widget-harness.mjs     # DOM 桩：状态机（快照、暂停/继续、排期让拍、边界、开关）
                                 #           + 音效（一次一响、CD、彩蛋、音量、降级）
node test/preview-server.mjs 19421
node test/cdp-squish.mjs         # 真实无头浏览器：过渡、支点、快照上真有像素、真的接着播
                                 #           + 素材真的能解码、AudioContext 在跑、CD 真的挡得住
```

真浏览器那一版会把"压扁中"的四张截图落到 `docs/dev-checks/`
（`v080-squish-{cooker,girl}[-before].png`，`--no-shot` 可跳过）。

## 掉盆（0.9.0）

按压小女孩时，除了压扁与按压音，还会**额外掷一个骰子**（`potChance`，默认 10%）：
掷中就让一个倒扣的不锈钢盆从天而降，**盆沿碰到她头顶那一刻**响一声「钢盆」，
同时"哐"地压扁一下再弹回。压扁、按压音照旧 —— 三件事互不影响。

| 想干什么 | 会怎样 |
| --- | --- |
| **一直点她** | 盆**一层层摞上去**：每多一个往上抬 22% 个盆高，还带 ±3.5% 块宽的水平抖动与 ±5° 的倾角抖动（生成时定下，之后不变） |
| **拖她** | 盆跟着走 —— 它是小女孩那一块里的一个子容器（`#dshca-pots`），不需要任何同步代码 |
| **改显示尺寸** | 盆同比缩放：它的宽度 = 块宽 × 1.08、下沿 = 块高 × 0.40（都是实测出来的比例，见下） |
| **拖盆到一旁** | 离原位超过"块宽 × 0.6"就**摘掉**（淡出 + 缩小），上面那些**重新摞下来**；拖得不够远则弹回原位 |
| **重播 / 关闭** | 盆跟着一起清掉（重播是从头演一遍） |

### 那些比例是怎么来的

素材能直接量：盆的透明 PNG 裁掉生成水印后是 1006×577；她的定格帧裁切是 900×1280、
头顶就在最上沿、脸在中段迅速张开。所以"盆该多大、该扣在哪"可以算出来，而不用猜：

- [tools/probe-head.mjs](dsh-corner-anim/tools/probe-head.mjs) 在真实浏览器里读她那块
  canvas 的 alpha 剖面（每行的内容左右边界），并可以把定格帧导出成 PNG；
- 再拿导出的那一帧与 `basin.png` 做叠加试摆，挑出与参考图最接近的一组：
  **盆宽 = 块宽 × 1.08、盆沿下沿 = 块高 × 0.40、顺时针倾 9°**（参考图里也是右侧偏低）。

### 叠放层级（这一条不做对就会出事）

```
        ┌─────────────────────────────┐
  z=2   │ 控制条 / 设置面板            │  ← 永远能点到，不会被盆盖住
        ├─────────────────────────────┤
  z=1   │ #dshca-pots（盆）            │  ← 只有盆本体接指针事件
        ├─────────────────────────────┤
  z=0   │ 画面层 + 点击 Q 弹的快照      │  ← 快照里**没有**盆（它是独立节点）
        └─────────────────────────────┘
```

- 盆**在快照之上**：点击 Q 弹拍的那张快照是从 canvas / 视频取的，里面本来就没有盆，
  所以盆必须留在快照之上 —— 否则一按她就"头上的盆不见了"。
- 盆**在控制条之下**：盆比她那块还宽、正好压在她头顶（也就是那块的上半部分），
  而悬浮按钮就在那里的右上角；顺序反了按钮就点不到。
- 容器自己 `pointer-events:none`，只有盆本体 `auto`：于是"拖盆"与"拖 / 压小女孩"
  天然互不打扰（盆的 `pointerdown` 里还会 `stopPropagation` 兜一道，
  `unitPointerDown` 里也用 `isPotTarget()` 再兜一道）。

### 音效

盆砸到头顶那一下放 [assets/basin.mp3](dsh-corner-anim/assets/basin.mp3)（1.05 秒），
与按压音**共用同一条 CD** —— 所以不会和「钢管」或合成音叠在一起（被 CD 挡掉时
这一次就是静的，不会用合成音顶替：那听起来会像"又按了一次"）。
它在**掉落开始**时就预热（掉落有 420ms，足够把 25KB 拉下来解码），

试听与排查：

## 拖动动画（0.10.0）

拖**小女孩那一块**的时候，她会被"拎起来"——播放 `assets/drag.webm`
（1112×834，VP9 + alpha，5.542s，循环），**松手立刻切回**她原来那一格。

参考实现是 VPet 的拖动状态机（[`vpet-drag-logic/`](../vpet-drag-logic) 里的
`MainDisplay.DisplayRaising` / `DisplayRaised`）：那边拖动时播 `Raised_Dynamic`
那一套"动态帧"、松手走 `C_End` 回到静态。这里用一段**循环**素材对应"动态"这一半，
收尾那一半按用户的要求做成"**立刻切回**"（不播收尾动作）。

几处刻意的边界：

| 边界 | 为什么 |
| --- | --- |
| **越过 3px 拖动阈值才起播** | `pointerdown` 那一瞬间分不清"点击"与"拖动"。放在阈值之后，按住不动的点击仍旧走 0.8.0 的点击 Q 弹 / 随机动画，不会因为手指抖一下就把拖动动画点出来。 |
| **不参与合并态** | 合并态（开场动画那一整块）本来就没有"她自己那一格"可以替换。 |
| **发送联动的两段、动画2 里她那段都自动让开** | 那几段都是**整幅替换**她的，两段抢同一块画面只会互相打架。 |
| **拖动期间她头上的盆一起让位** | 这段素材自己画着"被拎起来"的样子，浮在半空的盆会穿帮。松手立刻恢复。 |
| **排期器这一拍让过去** | 复用"正在播的不打断"那条判据：松手之后露出来的必须是她自己那一格，而不是一段已经跳过去的动画。 |
| **先占位、再收她的图** | 反过来的话，`play()` 到第一帧就绪之间的 100~150ms 里屏幕上什么都没有（"一按下拖动她就闪一下不见了"）；更糟的是 `playing` 迟到时那一步会落在"拖动已经结束"之后，拖动动画就留在屏幕上不走了。素材开头是透明的，所以先 `display:block` 再收她的图，观感上只是"姿势在这一瞬间换了"。 |

尺寸按**内容包围盒**摆（与待机 / 动作两段完全同一套：内容高贴齐她那一块、水平居中、
底边对齐）。`dragScale` 可以在觉得偏大偏小时微调（0.95 / 1.05 量级），
`dragRate` 是播放倍速。想关掉用 `dragAnim: false`。

## 电饭煲的两种随机动画（0.10.0）

### 一次点击，三个互斥的结果

点击（按下即触发，与拖动共用同一个手势）电饭煲时，**先掷两个骰子**：

```
                    ┌─ 20%（randomAChance）──→ 动画1「开盖 · 空锅」
  点一下电饭煲 ─────┤
                    └─ 10%（randomBChance）──→ 动画2「开盖 · 米饭热气」
                                 剩下 70% ──→ 点击 Q 弹 + 按压音效（0.8.0 的老行为）
```

**互斥是结构性的**，不是靠"两个都中了再挑一个"：代码里先问 A，只有 A 没中才去问 B。
所以既不会同时播，也不会出现"两次骰子都中了却只播了一个"的概率错配 ——
"点一下会演点什么"的总概率正好是 `randomAChance + randomBChance`。

掷中的那一次**不响按压音、也不压扁**：那两段素材本来就带原始音轨，再叠一声合成的
"软弹"只会互相盖住。

### 动画1：正常播放 → 倒放 → 立刻交回原样

```
0s ──────────── 5.06s ──────────────── 6.3s
│  正常播放（带声）  │  倒放回第 0 帧     │
└── 原来那口锅让位 ──┘                   └── 立刻把画面交回原来那格定格图
```

用户要的"播放结束后电饭煲变回原样（变动过程通过倒放动画1实现）"就落在这一段上：
**倒放本身就是那个"变回去"的过程**，倒放一结束立刻把她的画面交回定格图
（不是慢慢淡出，也不是倒放完再演一遍）。

倒放没有用 `playbackRate = -1`（浏览器普遍不支持，而逐帧 seek 在 VP9 上会疯狂重解码）：
元素**用正速率往前播**，只是把它的时间轴按真实时间轴往回拨 —— 视觉上是"原路退回"，
顺滑且只用正常的解码路径。时长由 `randomReverseMs`（默认 1200ms）控制。

### 动画2：她那段 + 电饭煲"在 5 秒内追到她"

两件事**同时**开始（不是等一方演完）：

1. **小女孩那一块**演 `assets/girl-basin.webm`（1280×720，5.042s，无声）：
   钢盆扣在头上、左右张望。这一段同样**独占画面**（她的定格图让位）。
2. **电饭煲**在 `randomFlightMs`（默认 5000ms）之内沿直线向她移动。

**"接触"是逐帧判定的，不是定时器假装出来的**：

- **移动量一次算清**：在"原位 → 她的位置"这条直线上按比例采样 160 个点
  （进度用 `smoothstep` 分布，起步不猛、落点不撞），用"她那块里的那张贴片"求
  每个点的重叠率，取最大的那个当终点。取的是**内容矩形**而不是整块 —— 她那块的
  盒子比屏幕上看得见的她大一截，拿盒子算会"看起来还离得远就算碰到了"。
- **逐帧推进**：`requestAnimationFrame` 每帧算一次当前重叠率，**哪一帧真的
  相交过半（≥50% 面积比）就算接触**，那一刻：
  - 电饭煲立刻归位（`transform` 与 `dshca-flying` 全部清掉）；
  - 她那段收工、画面交回她的定格图；
  - 两条动效节拍按"动画开始之前的状态"还回去（用户自己按过 ⏸ 的话不会替他打开）。
- **终点不越过接触点**：算完发现接触发生在 48% 处，那移动就走到 48% 为止 ——
  再往前只是白穿过去，画面上反而像穿模。
- **5 秒没碰到也算"已经贴上了"**：比如她自己被拖到了屏幕另一头。照样收工，
  绝不会留着一口飞在半路的锅。
- 判定用的贴片矩形取"**整段贴片包围盒**"与"**当前这一帧的矩形**"的**交集**：
  她那段素材里内容会漂（0.04s 那一帧 350,245,565,415；第五秒 371,213,509,419），
  取交集宁可判得稍晚，也不会"锅还离得老远就算碰到了"。

位置用的是 `transform`（两个 CSS 变量 + 一条很短的过渡抹平两次 rAF 之间的步子），
**绝不改 `left` / `top`** —— 拖动几何、以及"贴窗口右边缘"那套判据读的就是 `left`/`top`。

### 播放期间几条不变量

| 不变量 | 怎么保证 |
| --- | --- |
| **屏幕上永远只有一口锅** | 播放期间电饭煲那一块的定格图让位（`visibility`，不是 `display`，盒子还在）。 |
| **小女孩那一侧照旧** | 两道随机动画只换电饭煲那一侧的画面。动画2 里她本人被 `girl-basin` 替换，那由 `basinClipShown()` 管 —— 不是"随机动画一开就把她藏起来"（曾经这么写过，结果是动画1 播放期间她整个人凭空消失 5 秒）。 |
| **每一侧都恰好一格画面** | 自检每 60ms 采一次样、两侧分开数：同一侧不能"视频 + 定格图"同时亮，也不能什么都不亮。0.10.0 这一版就是靠它揪出上面那条"她凭空消失"和另外两处"闪一下没有了"。 |
| **锅那一块播放期间不接受点击 Q 弹** | 否则点一下会同时出现"压扁的快照"与"正在开盖的视频"。 |
| **排期停摆、演完原样还回去** | 与发送联动同一套做法：进来时记住 `scheduleOn`，收工按记住的值还回去。 |
| **重播 / 关闭 / 新一轮发送一律先收干净** | 定时器、rAF、`transform`、class、两段视频的播放状态一个都不留。 |
| **她头上摞着的盆一起让位**（0.10.1） | 她那段是"整幅替换她"的，盆留在原位会浮在坐姿动画的半空 —— 与 `girl.webm` / 拖动动画同一套 `refreshPotsVisible()` 判据；收工（接触复位 / 5 秒兜底 / 重播 / 关闭 / 新一轮发送）时原样恢复。 |
| **位移必须有东西消费**（0.10.1） | `applyFlight()` 写的 `--dshca-fly-x/y` 由 `.dshca-part.dshca-flying` 里的 `transform:translate(var(--dshca-fly-x,0px),var(--dshca-fly-y,0px))` 消费；自检断言的是**计算样式**（飞行中是 matrix、复位后回到 `none`），而不是"变量写没写"。 |

### 怎么现场验（不受概率限制）

```js
window.__dshcaRandom.probe()          // 谁在演、锅被挪了多远、她那段出没出画、两条概率
window.__dshcaRandom.play('lid1')     // 手动演动画1（不用等那 20%）
window.__dshcaRandom.play('lid2')     // 手动演动画2（含"飞过去 + 接触"）
window.__dshcaRandom.drag(true)       // 手动起拖动动画（false = 收）
window.__dshcaRandom.stop()           // 立刻收工
window.__dshcaRandom.debug()          // 每次判断 / 每次起播的账本 + 最近 40 次显隐判定
```

`play()` / `drag()` 都**不受骰子限制** —— 两道随机动画靠手点根本复现不了，
"那 20%"就是靠这个入口验的（自检里掷 400 次，实测 18~24% / 6~10%）。

想整体关掉用 `randomAnims: false`，或把 `randomAChance` / `randomBChance` 都设 0
（此时点击电饭煲完全回到 0.9.0 的行为）。

## 和「发送消息」联动（0.7.0）

这一节讲的是**行为和它的判据**，因为"什么时候该动"完全是靠观察页面得出的。

### 触发规则

| 时机 | 判据（与 class 名无关） | 动作 |
| --- | --- | --- |
| 点了「发送消息」 | 被点的元素正是那颗发送按钮 —— 优先 `aria-label` **精确等于**"发送消息"（实机就是这个），兜底才用"文案里含 发送/send/submit 且不含 停止/取消/stop"；或者是在输入框（`role=textbox` / `contenteditable` / aria 带"发消息"）里回车 —— 回车那条额外要求"页面上确实存在一颗可用的发送按钮"，否则聊天里的普通换行会被误判 | 播 `girl.webm` |
| 她演完 | `<video>` 的 `ended`（另有 `loadedmetadata` 时长兜底，素材坏了也不会卡住） | 按钮搬到电饭煲上方、隐藏小女孩、显示文案 + 起步计时器 |
| 模型开始输出 | **前置条件（0.7.5）**：DSH 的推理行不再是"流式尾巴"—— 也就是 `[data-variant="think"][data-state="running"]` 一个都不在（**「深度思索」结束**）。守住这一条之后，再看**回答正文容器**（`[class*="_markdown_"]`，排除 `_3GBCTG_` 那行"思考"）里的文本满足任一条：① 比"点发送那一刻"长了 ≥2 个字；② 长过之后连续 1.2 秒没再变。找不到正文容器时退回"全页文本总长"（兜底路径同样排除推理行） | 在**电饭煲原来的位置**播 `lid.webm`（带声），播完定格；**播完把蓝色文案与计时器一起收掉**（0.7.4）。**她还在演就先记下，等她演完立刻补播**；**还在深度思索就按住不播**（电饭煲保持原样，0.7.5） |
| 又发了下一条 | 同第一行（1.5 秒去抖，一轮收尾后重新武装） | 整套重置重来 |

> ⚠️ 为什么"开始输出"不能只看文本变长（0.7.5 补的一条）：DSH 每轮都挂一行「思考」，
> **那一行里的推理内容也是流式生成的**；更要命的是**过程行**——「正在分析请求 /
> 正在读取文件 / 正在调用工具」（`message.stepProcess.*`）——它们在推理行**外面**，
> 任何按文本长度做的排除都排不掉，于是"页面文本在变长"在模型还没想完时就成立。
> 所以真正把关的是推理行自己的 `data-state`：**它还在 `running`，开盖就不许播**。
>
> ⚠️ 为什么计时不能代替判据：计时器从**事件 1 收尾**开始跑，它衡量的是"这轮对话
> 已经过了多久"，跟"模型有没有开始输出"是两件事 —— 所以不能拿它当开盖的触发条件。

两处"会猜错"的地方都有逃生门与诊断：

- **按钮找不准** → 配 `sendSelector: '#你的按钮'`，它优先于语义猜测。
- **想完全关掉** → `sendHook: false`，挂件立刻回到 0.6.0 的行为。
- **想现场排查** → 控制台：

```js
window.__dshcaSend.findButton()   // 现在认定哪颗是发送按钮（null = 没找到）
window.__dshcaSend.debug()        // 每次判断的依据与时间戳
window.__dshcaSend.probe()        // 观察器内部状态：基线、当前总长、阈值、是否还在深度思索
window.__dshcaSend.simulate()     // 手动把事件 1 + 事件 2 各走一遍，不用真发消息
window.__dshcaSend.output()       // 只触发事件 2（开盖那一段）
window.__dshcaSend.reset()        // 复位到初始布局
```

### 布局

```
        ┌──────────────┐
        │ ↻ ⏸ ⇄1× ▾ ✕ │  ← 原先在小女孩身上的五颗按钮，搬到了电饭煲上方
        ├──────────────┤
        │  开盖（带声）  │  ← 0.7.3：模型开始输出时**原地**盖在电饭煲上播，
        │  （原来那口锅） │     播完停在最后一帧（原来那口锅同时藏起来）
        └──────────────┘
         肥鱼已经煮饭：      ← 蓝色文案（sendLabel / sendLabelColor 可配）
        ┌────────┐
        │ 00:12  │         ← 计时器：事件 1 收尾那一刻开始跑
        └────────┘
                           ← 0.7.4：开盖播完，上面这文案 + 计时器一起收掉
```

开盖那段是**替换**电饭煲的：它自己就画着一口完整的锅（从合盖到开盖、冒出小女孩），
所以播放期间原来那块定格图被藏起来（`visibility`，不是 `display` —— 盒子还在，
拖动与计时器那一列的位置都不会跳），屏幕上始终只有一口锅。
它播完**不清屏**：锅与探头的她继续停在最后一帧，只是把文案与计时器收走；
下一条消息才把这一整套（含文案与计时器）复位重来。

小女孩那块在这一阶段是**整个隐藏**的（不是只藏画面），所以她的定格 canvas 与
两条节拍的动画层都不会露出来；两条节拍的定时器同时停摆，不再抢画面。而事件 1
**播放期间**（她还在演的时候）反过来：那一段**独占画面**（0.7.3）—— 定格 canvas
与两条节拍一起让位，否则半透明的跑出动画底下会露出"原先那张她"，看起来像两个她。

### 两个素材都是"内容只占画幅一小块"

`girl.webm` 1920×1080 里内容只占 **38%** 宽，`lid.webm` 2560×1440 里内容只占
**36%** 宽（两份都是 VP9 + alpha，浏览器实测透明像素分别占 76.6% / 84.8%）。
所以这两份**必须按内容包围盒摆**，否则一个只剩头顶、一个小得看不见 ——
和 `idle` / `act` 用的是同一套"读 alpha 量内容框"的做法。

`lid.webm` **保留着原始 Vorbis 音轨**（这是你明确要求的，也是随包唯一会出声的素材）：
它在用户点过发送之后才起播（所以有用户手势），万一仍被自动播放策略拦下，会退回
静音放画面并在右下角出现一个可点的小喇叭。

## 配置

全部可选 —— 不写就用默认值。改 `~/.dsh/profiles/<profile>/cordis.patch.yml`：

```yaml
- insert:
    - id: dsh-corner-anim
      name: dsh-corner-anim
      config:
        enabled: true            # false = 完全不加载
        corner: top-right        # top-right | top-left | bottom-right | bottom-left
        width: 220               # 初始显示宽度（px），也是面板「重置」的目标值
        minWidth: 80             # 面板滑杆下限（px）
        maxWidth: 600            # 面板滑杆上限（px）
        offsetX: 20              # 距视口左右边缘的间距（px）
        offsetY: 20              # 距视口上下边缘的间距（px）
        opacity: 1               # 0.05 ~ 1
        draggable: true          # 是否允许拖动
        showControls: true       # 是否显示「重播 / 排期 / 间隔 / 折叠 / 关闭」与设置面板
        rememberPosition: true   # 拖动后是否记住位置
        split: true              # 播完后是否拆成「左电饭煲 / 右小女孩」两块
        splitAutoDetect: true    # 是否按最后一帧的 alpha 自动找分割线
        splitRatio: 0.5          # 自动探测不可用时的兜底分割比例（0.05 ~ 0.95）
        idle: true               # 小女孩是否播待机动画 assets/idle.webm
        idleEvery: 5000          # 待机动画基准间隔（毫秒；实际 = 基准 × 间隔倍率）
        idleScale: 1             # 待机动画相对小女孩那块的缩放（0.1 ~ 10）
        act: true                # 小女孩是否播动作动画 assets/act.webm
        actEvery: 15000          # 动作动画基准间隔（毫秒；实际 = 基准 × 间隔倍率）
        actScale: 1              # 动作动画相对小女孩那块的缩放（0.1 ~ 10）
        sendHook: true           # 是否启用「发送消息」联动（false = 回到 0.6.0 行为）
        sendSelector: ''         # 指定"发送按钮"的 CSS 选择器；留空 = 自动按语义找
        sendGirlScale: 1         # 点发送后那段小女孩动画的缩放（0.1 ~ 10）
        sendLidScale: 1          # 开盖动画的缩放（0.1 ~ 10）
        sendLabel: '肥鱼已经煮饭：'  # 计时器上方的文案
        sendLabelColor: '#3b82f6'   # 该文案的颜色（只接受字面颜色）
        sendLidAudio: true       # 开盖动画是否放声（素材保留着音轨）
        clickSquish: true        # 电饭煲 / 小女孩的点击 Q 弹（false = 按住不再压扁）
        pressSound: true         # 点击 Q 弹的按压音效（false = 完全静音）
        pressVolume: 0.6         # 音效音量 0 ~ 1（合成音的峰值与两条素材音的 gain 都乘它）
        pipeChance: 0.07         # 按压电饭煲时改响 assets/pipe.mp3 的概率（0 = 从不，1 = 每次）
        pipeVolume: 0.5          # 「钢管」相对 pressVolume 的倍率（0.5 = 减半）
        potChance: 0.1           # 按压小女孩时掉一个盆的概率（0 = 关掉，1 = 每次都掉）
        randomAnims: true        # 电饭煲两种随机动画的总开关（0.10.0）
        randomAChance: 0.2       # 动画1「开盖 · 空锅」的概率（播完倒放回原样）
        randomBChance: 0.1       # 动画2「开盖 · 米饭热气」的概率（她那段 + 锅追过去）
        randomFlightMs: 5000     # 动画2 里电饭煲"追到她"的上限时长（毫秒）
        randomContactScale: 0.95 # 动画2 里她那一段相对她那块的高度比例
        randomReverseMs: 1200    # 动画1 倒放的时长（毫秒）
        randomRiceScale: 1       # 动画2 素材（米饭热气）的内容倍率
        randomEmptyScale: 1      # 动画1 素材（空锅）的内容倍率
        dragAnim: true           # 拖小女孩时是否播"拖动动画"（false = 回到 0.9.0 的拖动）
        dragScale: 1             # 拖动动画相对她那块的高度倍率
        dragRate: 1              # 拖动动画的播放倍速（0.25 ~ 4）
```

优先级与生效条件：

- `corner` / `offsetX` / `offsetY` 只在**没有记忆位置**时生效。
  想回到配置的角落，清掉 `localStorage` 里的 `dsh-corner-anim:pos:v1`：
  `localStorage.removeItem('dsh-corner-anim:pos:v1')`。
- 面板里调过的**大小优先于 `width`**，但始终夹在 `[minWidth, maxWidth]` 内。
  想回到配置值，点面板里的「重置」，或清掉 `dsh-corner-anim:size:v1`。
- 面板 / 控制条里调过的**动画间隔倍率优先于 `idleEvery` / `actEvery`**，
  夹在 `[0.25, 4]` 内，并且是**乘法** —— 例如 `idleEvery: 8000` 配上 2×
  就是待机 16 秒、动作 30 秒（`8000 × 2` 与 `15000 × 2`）。
  想回到配置值，点「重置」或清掉 `dsh-corner-anim:speed:v1`。
- `showControls: false` 会连设置面板一起去掉 —— 面板属于控件面的一部分。
- 两块拆开后的摆放位置各自记在 `dsh-corner-anim:pos:cooker:v1` /
  `:girl:v1`。**整体被拖动过就作废**，下次拆分重新从整体位置推导 ——
  这样「把整块挪个地方」和「把两块摆开」两种意图不会互相打架。
- `idle: false` / `act: false` 各自关掉一段：关掉一段后另一段照常按自己的节拍走，
  只是同时到点的挤位问题自然消失。**两段都关**就回到 0.3.0 的行为：
  播完只留两张定格图，Debug 与间隔按钮也一起消失。
- `split: false` 时没有「小女孩那块」可站，两段动画都不会出现。
- 觉得动画里的小女孩比定格图明显偏大或偏小，用对应的 `idleScale` / `actScale`
  微调（`0.95` / `1.05` 这种量级就够，见下面「动画是怎么摆正的」）。
- `idleEvery` / `actEvery` 最小 1000ms、最大 1 小时；写小了会被夹上来。
  想让某一段"偶尔露个脸"，把它调大即可（比如 `actEvery: 120000`）。
  注意乘上倍率之后仍受同一对上下限约束（0.25× 时 `idleEvery: 5000` → 1250ms）。
- `clickSquish` 是**配置文件级别**的开关（和 `idle` / `act` 一样，面板里没有对应
  控件）：`false` 只关掉"按住压扁"，拆开、两条节拍、发送联动都不受影响。
  同组的 `pressSound` / `pressVolume` / `pipeChance` / `pipeVolume` 也是配置文件级别 ——
  它们只作用于**按压音效**：`pressSound: false` 静音但压扁照旧；`pipeChance: 0`
  等于"没有彩蛋"（永远响合成音），`1` 则是"每次按压电饭煲都响钢管"（调试时好用）；
  `pipeVolume` 只压「钢管」那一条，不影响普通按压音。
- `potChance` 是**掉盆**的概率（`0` = 关掉这个事件，`1` = 每次按压小女孩都掉一个，
  调参时很有用）。它与 `clickSquish` 一样属于"按压小女孩"这条交互：`clickSquish: false`
  会连它一起关掉。
- `randomAnims: false` 让"点击电饭煲"完全回到 0.9.0：只剩点击 Q 弹 + 按压音效。
  只想调概率就不必动总开关 —— `randomAChance: 0` 等于"从不播动画1"，
  两个都设 `0` 与 `randomAnims: false` 等价。想把两道动画当调试素材反复看，
  两个都设 `1` 也行（互斥的结构保证它们不会同时播），但那时**每一次**点击电饭煲
  都会被动画接管、点击 Q 弹再也出不来（它只在两个骰子都没中时才轮到）。
  `randomReverseMs` 是动画1 倒放的时长：调小 = "啪"地合回去，调大 = 慢慢倒。
- `dragAnim: false` 让拖动完全回到 0.9.0 的行为（拖动期间她那一格原样不动）。
  `dragRate` 是那段素材的播放倍速（默认 1，即原速）。

配置值做了容错：字符串数字会转成数字，越界会夹到合法区间，
`minWidth` / `maxWidth` 写反了会自动纠正（保证 `width` 一定落在两者之间），
未知字段直接忽略。写错任何一项都不会导致插件不加载。

> 里**，重编码很容易把它压没；`-c copy` 只搬字节，绝不会动 alpha 结构。

只要新素材的两个主体之间有竖直透明缝隙，就照样能拆；实在找不到缝隙时，
才退回 `splitRatio` 按比例切。两段动画的内容包围盒也是运行时各自量的，
所以换一段构图、留白完全不同的动画视频也不用改任何配置。

## 实现说明

### 两条注入通道

DSH 有 Web（浏览器）与桌面（Electron 壳）两种形态，注入方式不同，本插件两条都实现了：

| 形态 | 通道 | 说明 |
| --- | --- | --- |
| Web | `webServer.tapIndex(html => …)` | 对每个 `index.html` 响应追加 `<script defer src=…>`。 |
| 桌面 | `webserver/index-inject` 结构化行 | 桌面壳的 index.html 由安装包静态 dist 直出（`dsh-app://app/`），**永远不经过** `renderIndex()`，所以 `tapIndex` 在桌面端不生效。 |

两个关键坑（照抄 `dsh-whale-widget` 在 issue #152/#153/#154 的实测结论）：

1. **注入行必须在 `apply()` 最开头注册**，不能放进 `inject` 回调。
   桌面端的注入表是**宿主启动时一次性收集**的，订阅晚于那次收集就永远进不了表 ——
   表现就是「插件装了、宿主半区活着、客户端半区从未被请求」。
   所以本插件**没有**对象级 `inject`，需要服务的部分放在局部 `root.inject([...], cb)` 里。

2. **只能推内联 `script` 行，不能推 `script-src` 行**。
   页面侧解释器对 `script-src` 是「加载失败即 reject」，那个 reject 会带走
   `__DSH_BOOT_READY__`，**DSH 直接起不来**。而 `script` 行只是
   `createElement + textContent + append`，没有 await，不可能失败。
   行内由它自己建 `<script src=…>` 并且**吞掉 `onerror`** ——
   路由在就正常加载，路由不在就静默失败，宿主永远不因为这个插件起不来。

### 为什么「停在最后一帧」不用额外处理

HTML 规范里，未设 `loop` 的 `<video>` 播放结束后，元素**继续显示最后一帧**，
`currentTime` 停在 `duration`。这就是需求本身要的行为，所以：

- **绝不设 `loop`**（设了就永远在循环，看不到「停住」）；
- 不在 `ended` 里重置 `currentTime`、不淡出、不移除节点；
- 只做两件不改变该行为的事：显式 `pause()`；以及一个纯兜底 ——
  只有当 `currentTime` **确实被谁重置回开头**时，才把它拨回末尾
  （正常路径不触发，因此不会引入跳帧闪烁）。

### 拖动为什么用 Pointer Events + `setPointerCapture`

`pointerdown` 时捕获指针，之后的 `pointermove` / `pointerup` 会直接投递给挂件，
即使指针划出挂件、划出窗口也不会丢事件。位移小于 3px 视为点击而非拖动，
避免和悬浮按钮打架。根节点 `touch-action: none`，触屏拖动同样跟手。

### 拆分是怎么找分割线的

不是「找最宽的一条空列」—— 那样会挑中**画面右侧的空白边距**（这份素材右边有
300px 纯留白，比两个主体之间那条缝还宽）。这是实测踩到的坑，现在的规则是：

1. 把最后一帧缩到 256 宽的小画布，取 `getImageData`，算出每一列的 alpha 覆盖量；
2. 找出所有空列区间，但只认**左右都不贴画面边缘**、且**两侧各自都还有 ≥15% 内容**
   的那些 —— 贴边的空白是留白，不是缝隙；
3. 取其中最长的一条，以它的中点为分割线；
4. 左右两块再各自收紧到**自己内容的包围盒**（行方向也只扫自己那几列，
   否则另一侧的内容会把这一侧的上下边界撑开）；
5. 每一块直接以 `<video>` 为 `drawImage` 源、只画自己那块矩形，
   不需要全尺寸中间画布。

这份 2K 素材实测的拆分结果是：电饭煲 `[220, 390, 1060, 960]`、
小女孩 `[1340, 40, 900, 1280]`（源像素 x, y, w, h），中间 60px 的透明缝两块都不占。

跨源素材会把画布标记为 tainted，`getImageData` 会抛异常 —— 这不影响画面，
只是读不到像素，于是退回 `splitRatio` 按比例切；`splitAutoDetect: false`
可以强制走这条兜底路径。

### 小女孩为什么贴在窗口边框上（0.7.3）

上面那两块坐标里，小女孩的裁切框是 `[1340, 40, 900, 1280]` —— 她右边缘在 2560 的
第 2240 列，**右边还有 320 源像素（12.5%）的纯透明留白**（那是素材作者给构图留的边距）。
"就地拆开"会把这段留白也算成她的位置，于是挂件贴在右上角时，她就停在离窗口右边缘
40~50px 的地方 —— 看着像悬在半空中，而不是站在窗口边框上。

所以 0.7.3 起，拆分时对两块用两条不同的规则：

| | 规则 |
| --- | --- |
| **电饭煲** | 落在它在帧里的位置（`base + box × k`），拆开前后完全重合。 |
| **小女孩** | 只挪她一个人：`x = 窗口宽 − 她的显示宽 − 2px`，即**贴住窗口右边缘**；竖直方向保持帧内的行，整块再夹进视口（`clampInside`，与拖动用的 `clampPos` 是两套：拖动允许最多 56px 露在窗口外，摆放不允许）。 |

两个边界都考虑到了：

- **挂件在窗口左半边时（`corner: top-left` 之类）不贴边** —— 硬把她拽到右边框会让她
  横穿整个窗口、离电饭煲十万八千里；那时保持帧内位置，只保证完整可见。
- **你自己拖动过她之后就不再自动贴边**（`girlHugged` 置假）：改窗口大小、改显示尺寸
  都不会把你摆好的位置拽回去。没拖过时，这两件事都会按新尺寸/新窗口重新贴一次边。

### 动画是怎么摆正的

这是整个插件里最容易做错的一步。三份素材的**画幅与人像占比都不一样**：

| | `anim.webm` 里的小女孩那块 | `idle.webm` | `act.webm` |
| --- | --- | --- | --- |
| 素材分辨率 | 裁出来的 900 × 1280 | 1440 × 1920 | 1440 × 1916 |
| 人像在画面里的占比 | 占满整块（裁的就是包围盒） | 只有中间一条：内容包围盒 1259 × 1728，四周还各有 90~190px 透明留白 | 同样只在中间（运行时量） |

所以「把 `<video>` 铺满小女孩那块」是错的：`object-fit` 只有两种结果 ——
要么保持等比、留白把人物缩小，要么拉伸、把人物压扁。两种都不对。

现在的做法是**按内容对齐**，每一路各自量、各自摆：

1. 起播前先把该素材画进一张 256 宽的小画布，读一次 alpha，
   算出**内容包围盒**（阈值取 alpha > 24，免得抗锯齿边缘把包围盒撑胖）；
2. 让**内容高度**等于小女孩那块当前的显示高度（再乘该路的 `idleScale` / `actScale`）；
3. 内容**水平居中**、**底边对齐** —— 脚踩在同一水平线上，比"顶部对齐"稳得多；
4. 于是 `<video>` 自身的 CSS 尺寸与偏移是反推出来的，画幅的透明留白
   自然被排到框外，不会被当成"人物的一部分"。

实测结果（无头 Chromium 读真实布局）：小女孩那块 77 × 126.7 CSS px 时，
待机层是 91.25 × 121.67 px、偏到 `(-8.04, -6.08)` ——
待机内容正好覆盖小女孩那块的 126.7px 可见高度，左右各溢出约 1.5px（人物的宽度
本来就比裁切框宽 ~4%，体量对得上）。

把「定格的那一帧」和「动画素材的内容框」归一化后叠在一起（红 = 定格，青 = 动画），
两者轮廓几乎完全重合，只剩动作带来的细微边缘 —— 这也是为什么切换看起来不跳：

```text
定格帧裁切            动画素材内容框          叠加（红 = 定格，青 = 动画）
┌──────────┐        ┌──────────┐        ┌──────────┐
│  小女孩  │   ≈    │  小女孩  │   →    │  灰 = 重合│  ← 只剩动作的细边
└──────────┘        └──────────┘        └──────────┘
```

量不到像素时（跨源素材 / canvas 不可用）退回「整幅等比」，此时用对应的 scale
手动调到看着合适为止；某一路的素材读不出来时只丢这一路，另一路照常轮播，
**绝不会让小女孩那块变成空白**。

### 排期器：两条节拍，一段画面

```
播放第一段 ──ended──▶ 定格最后一帧 ──rAF──▶ 拆分两块 + 挂上两路 <video>
                                                      │        （都先隐着）
                                                      ▼
                                            ┌─── 排期器（每拍只选一路）───┐
                                            │  待机 idle.webm   每 5 秒    │
                                            │  动作 act.webm    每 15 秒   │
                                            └──────────────┬──────────────┘
                                                           ▼
                shownKind = null                  shownKind = 'idle' / 'act'
                → 定格 canvas 出画                 → 该路 <video> 出画（播一遍，停在最后）
                  （只在首拍之前）                            │
                                                             │ 播完 → 就停在这一格（0.6.0）
                                        ⏸按钮：整条节拍停摆，画面**原样冻住**（仍是这一段）
                                        ▶按钮：从当下重新计时，冻住的这一格留着，下一拍起播
                                        ⇄按钮：只改节拍长度，不打断正在播的那段
```

几个刻意的取舍：

- **一拍只上一路，撞车动作优先**：两条节拍各自 `dueAt`，到点的那些里挑一路；
  5 秒与 15 秒每 15 秒必然同时到点，那时固定让动作动画上。
- **正在播的不打断**：一拍到点时若已有动画在出画，这一拍**直接跳过**
  （`dueAt` 往后挪一个周期）。跳过而不是排队 —— 排队会让节拍越欠越多，永远追不上。
- **播完停在自己的末帧**（0.6.0）：一段播完之后**什么都不做**。
  `<video>`（`loop = false`）在 `ended` 之后本来就继续显示最后一帧，它继续占着
  "唯一一段画面"的位置，直到下一拍到点被接走。旧实现排了一个 200ms 的"收工"定时器，
  到点把层撤掉、露出下层定格帧 —— 那正是"每段动画演完，小女孩都一跳回到开场姿势"的成因。
- **改间隔 = 重新定拍**：倍率一变，两张表按新周期重建，并**一起从当下重新起算**。
  不保留原来的相位：两路各自带着旧间隔攒下的漂移走，1:3 的比例很快就不成立，
  而"同时到点"的判定恰恰依赖这个比例。
- **坏素材要连节拍表一起摘**（0.6.0 修的）：只从 `animSlots` 里删掉是不够的 ——
  排期器按 `periods` 里的到期时刻决定下一次唤醒，那一项留着就会一直为一段
  已经不存在的动画空转，还会把下一次唤醒定在比另一路真正该播的时刻更早的地方。
  `dropClip()` 现在把节点、槽位、节拍表一起收拾干净。
- **`dueAt` 拨到未来再排定时器**：被跳过的那一拍可能落在过去，直接拿
  `dueAt - now` 当等待时长会得到负数（被 `setTimeout` 当成 0），于是同一时刻反复到点、
  动画连环起播。所以排期前先把每个到期的 `dueAt` 拨到未来（保持原来的相位）。

### 屏幕上永远有且仅有一段画面

这是 0.5.1 之后的硬不变量，0.6.0 起连"播完之后"也归它管。

实现上只有**一个判据**：模块级的 `shownKind` —— 当前该出画的是哪一路
（`null` = 还没有任何动画出过画，画面归定格 canvas）。任何状态变化都只调一个函数：

```js
showOnly(kind)   // 唯一落点：设 shownKind，把该路推到 DOM 末尾并以真实
                 // 布局尺寸显示；其余各路 visibility:hidden 且 pause()；
                 // 最后由 overlayShown 决定定格 canvas 是否让位
```

- **只认 `shownKind`，不接受间接推断**。早先几版分别用过"层挂没挂上"、
  "排期器开没开"、"元素谁后 append"、"currentTime > 0 算占用" 这些条件，
  每一个都对应过一类 bug（露下层 / 连续两拍 / 顺序错乱 / 冻死）。
- **`kind` 为空时保留当前画面，而不是交还定格帧**（0.6.0 的关键改动）：
  上一段那格已经 `ended`、停在它自己的末帧上，它就是那"唯一一段画面"。
  只有"谁都没有可显示的一格"（首拍之前）才轮到定格 canvas。
- **`visibility` 而不是 `display`**：隐藏的那几路仍然占位、仍能量到尺寸、
  仍按各自的素材宽高比排好版，所以切回来是瞬时的、无需重新测量。
- **显式摆正堆叠顺序**：同层绝对定位的 `<video>` 之间，DOM 顺序就是谁在上层，
  所以 `showOnly()` 会把当前这一路 `appendChild` 到末尾（只挪位置，不重新加载）。
  靠"谁恰好后挂上"是不牢靠的：重播、换素材、丢了一路之后顺序都会变。
- **兜底也不换人**：`settleVisibility()` 只在"`activeSlot` 还在不在"之间二选一，
  **不会**"挑一路还在的顶上"—— 那正是"另一段被错误顶上来"的来源。
  某一路素材坏掉时，正确的反应是让它自己那格定格，而不是换一段播。
- **暂停不改画面**：只 `pause()`，冻住的仍是当前这一段，`shownKind` 不动。
- **继续保留画面、只放掉排期的位**：冻住的那一格不再算"在出画"（否则它永远不会
  `ended`，会把后面的每一拍都吃掉），但**画面不撤** —— 下一拍到点前，屏幕上还是它。

浏览器里的验证方式：预览页每 50ms 采样一次真实 `style.visibility` + canvas 状态，把"屏幕上到底有几段画面"记进 `window.__violations`，把"动画出过画之后又退回
开场定格帧"记进 `window.__fallsBack`，并跑一条完整的
`暂停 → 继续 → 再暂停 → 再继续` 时间线。实测两者都是**空数组**，
时间线里每一格都是单一画面（`idle(playing)` / `idle(paused)` / `idle(holding)` / `act(playing)`）。
判据里 0.7.3 起也算上**跑出动画**（`girl-clip`）：她在演的时候，那一格必须是
`girl-clip` 且 `count = 1`；她演完那一轮整个右块藏起来之后记作 `girl-hidden`
（小女孩这一侧没有画面，"两张图"这件事无从谈起）。

0.8.0 起**点击 Q 弹的快照也算这一格画面**：按住时它替掉被拍下来的那一层
（那一层被写成 `visibility:hidden`，并且 `showOnly()` 在每次收敛之后都会**再把它
按回去** —— 否则"暂停 / 继续"那条路径会让原来那一层从半透明的快照底下透出来，
看上去就是两个她）。松手后还多一段 260ms 的"回弹中"（`squishSettling`），
排期器在这一段里同样不许接走画面。

### 暂停为什么不再露馅

0.5.0 修掉的那个 bug，根因是**把"层挂没挂上"当成了"画面归谁"**：

- 旧实现里暂停走的是"撤层"那条路，于是层一撤，下面那张定格 canvas 就露出来了 ——
  画面从"某个动作"一跳回到"开场最后一帧"，非常突兀。
- 现在判据收在 `shownKind`（见上一节）：暂停只是 `pause()`，`shownKind` 不动，
  所以屏幕上还是原来那一段，只是不动了。
- 0.6.0 起"播完收工"那个 200ms 定时器已经被整个删掉，所以暂停时不再需要撤它，
  也不存在"它到点把画面交还定格帧"这半条路。
- **继续**时从当下重新计时（不补播错过的拍），冻住的那一格继续留着。
  0.5.1 之前这里没有把 `activeSlot` 放掉，于是冻住的那一格把后续所有节拍都吃掉了
  （它既不会 `ended`，又被算作"在出画"）—— 表现就是"继续之后别的动画再也没出现过"。
- 重播 / 关闭仍然会把层整体撤掉（那时**应该**回到整体或消失）。

### 面板定位与「不误拖」

`pointerdown` 会先判断目标是否落在控件子树里（按钮条 / 设置面板 / 播放提示），
是就直接返回 —— **点滑杆不会顺手把挂件拖走**（测试里对面板背景、滑杆、预设按钮
三种目标都验证过）。面板与按钮条在拆分后会被**搬到小女孩那块里**，
面板定位因此以「当前宿主」为基准，展开时按「下方优先、放不下翻上方、
水平夹进视口」算一次坐标；量到的面板尺寸会缓存，
所以拖动过程中的重排开销只是一次样式写入。

一个已知取舍：宿主带 `touch-action: none`（拖动需要），而 `touch-action`
在祖先与自身之间取交集，所以**触屏设备上拖滑杆可能被浏览器抢去做滚动手势**。
鼠标操作完全不受影响；这属于桌面优先的取舍。

```powershell
#   http://127.0.0.1:19399/?idle=1       额外回报动画层：布局 + 两条节拍的真实时间线
#   http://127.0.0.1:19399/?idle=1&ab=1  再叠一张「定格帧 vs 动画帧」的红青对照图
#   http://127.0.0.1:19399/?speed=1      自动点档位按钮 + 拉动间隔滑杆，回报读数
#   http://127.0.0.1:19399/?sched=1      按脚本点两次「暂停 / 继续」，验一遍状态机
#   http://127.0.0.1:19399/?send=1       造一个假「发送消息」+ 会变长的回答，跑完
#                                        0.7.0 的两条事件并逐阶段回报几何

#                                        拖动动画 / 动画1 / 动画2 各跑一遍

```

前两套是零依赖的纯 Node 脚本（`node:assert` + `node:vm`），当前分别是 24 项与 128 项断言。
`preview-server.mjs` 会把预览页跑一遍插件**自己的 `tapIndex`**，所以它连注入通道一起验证，
而不是手写一个 `<script>` 把问题盖住。

它的 DOM stub 里带一个**合成画布**：`getImageData` 返回「除了中间一条透明竖带以外
全不透明」的假帧，于是拆分逻辑可以在确定性输入上被断言（分割线必须落在那条竖带正中、
两块必须各自裁到自己的内容、边缘空白必须被忽略、tainted 必须走兜底）。
DOM stub 还带一个**可控时钟**（`env.advance(ms)` + `env.clock`），
因为排期器是按墙钟时间工作的，另外两路动画的 `<video>` 会预置**真实素材的时长**
（`idle.webm` 5.048s / `act.webm` 5.003s），所以"停在末帧"能按真正的
`duration` 位置来断言。动画相关的断言覆盖：

- 拆分时挂上两路但都不播，**屏幕上只有定格帧**（`assertSinglePicture` 逐个场景验）；
- 第一拍在 5s 起播待机；落在播放中的那一拍**不打断**、不另起；
- 两段各自按 `idleEvery` / `actEvery` 走，同时到点时**动作优先**（反复验证，不只第一次）；
- 一条精确到毫秒的时间线：4s 待机 → 6s 动作 → 8s 待机 → 12s 撞车动作优先；
- **播完停在它自己的末帧**：`ended` 之后那一路仍可见、`currentTime` 正好等于 `duration`，
  而且**开场定格帧绝不回来**（每个自由跑动的步骤都断言一次）；
- 跑满四分钟的交错节拍，**每一步都断言"恰好一段画面"**（不会两段、也不会空）；
- 每段按各自素材的宽高比、按内容贴到小女孩那块（两路各自量、各自摆）；
- **暂停冻住画面且绝不露出下层定格帧**（暂停后不留任何待发定时器）——
  这条就是 0.5.0 修掉的那个 bug，作为回归断言留着；
- **继续会放掉排期的位、但画面不撤**：下一拍照常起播，且之间屏幕上
  仍然恰好一段画面（她自己的末帧）—— 这两条合起来是 0.5.1 / 0.6.0 的回归断言
  （把旧逻辑放回去，它们会失败）；
- 暂停期间时钟无论走多久都不出画；
- 播完到点就交接（不闪定格帧）；
- **动画间隔**：档位按钮循环 0.5×/1×/2×/4× 并写进存储、滑杆对数刻度两端与中点、
  面板预设与控制条同步、重载后生效并驱动第一拍、坏值/越界值的兜底、
  改间隔不打断正在播的那段、暂停中改间隔在继续时生效；
- 重播 / 关闭时两路一齐退场、排期不再复活；
- `idle:false` / `act:false` / 两个都关 / `split:false` 四个开关；
- 某一路素材坏掉时只丢这一路（连节拍表一起摘干净），另一路照常；
- **发送联动**（0.7.0，用一套"假 DSH 壳"驱动）：点发送播小女孩那段、她演完按钮
  搬到电饭煲上方且她本人隐藏、蓝色文案与计时器出现并逐秒走字、回答开始变长时
  开盖那段起播（且**没有静音**）、它停在最后一帧、再发一条整套重置；
  以及判据本身的边界 —— 挂件自己的点击不算、停止按钮不算、回车只在有发送按钮
  时才算、输入法组合中不算、`sendHook:false` 完全不介入、`sendSelector` 优先、
  `split:false` 不炸、关闭挂件时监听器与计时器一个不留；
- **"思考"那一行的流式文本不算"开始输出"**（0.7.1 的回归断言）：壳里按实机结构
  造出 `div._3GBCTG_row`（含流式推理预览）+ `div._markdown_…`（回答正文），
  推理长到 320 字都不许触发开盖，只有正文变长才触发，且一轮只触发一次；
- **一轮在"她还演着"的时候就输出完了**（0.7.2，问题 1 的回归断言）：输出在她还在演
  时就被抓到、但**不与她抢画面**，等她一演完立刻补播开盖；
- **屏幕上只有一口电饭煲**（0.7.2，问题 3 的回归断言）：开盖那段播放期间原来那块
  定格图被隐藏，下一条消息再恢复。
- **小女孩停在窗口右边缘**（0.7.3，问题 1 的回归断言）：用一个带 12.5% 透明右边距的
  合成帧跑拆分，断言她正好停在 `窗口宽 − 2px`、电饭煲一动不动；改窗口大小、改显示
  尺寸都会重新贴边；**拖动过她之后就不再贴边**；窗口很窄时她也不会被挤出左边；
  `corner: top-left` 时不会被横拽到右边框。
- **跑出动画独占画面**（0.7.3，问题 2 的回归断言）：两种"原先的图"各验一遍 ——
  底下压着待机动画的末帧时、以及底下是拆分时裁出的定格 canvas 时，她一开始跑出，
  两路节拍与定格 canvas 都必须不可见（`scheduledVisible` 为空 + `canvasVisible` 假），
  并且屏幕上恰好一段画面；演完再把画面交回去。
- **重播之后跑出动画还挂在右块上**（0.7.3）：重播会先摘掉两块（连同她那段视频），
  断言第二轮它被重新挂回新的右块上、并且真的又播了一次。
- **开盖原地播放**（0.7.3，问题 3 的回归断言）：它挂在 `<body>` 上而不是计时器那一列里；
  内容宽 = 电饭煲宽、内容左缘 = 电饭煲左缘、内容下沿 = 电饭煲下沿；拖动电饭煲时
  它跟着走；文案/计时器那一列仍在它下方且不被压住。
- **开盖播完清掉文案与计时器**（0.7.4）：开盖 `ended` 之后那一列不再显示、并且
  **没有任何 interval 还在跑**（把时钟往前推 3 秒，读数也不动）；开盖画面仍停在
  最后一帧；下一条消息走完事件 1 之后，那一列重新出现并从 `00:00` 开始走字。
- **「深度思索」期间不许开盖**（0.7.5）：推理行仍是 `data-state="running"` 时，
  正文长出来也不播（`probe().heldForReasoning === true`、电饭煲那一块没有任何变化）；
  **过程行**（「正在分析请求 / 正在调用工具」，在推理行外面、把文本长度判据拉起来）
  一直长也一样按住；把推理行翻成 `data-state="ok"`（去掉 `data-streaming`）之后，
  下一拍就播 —— 顺序在诊断账本里是 `output-held-reasoning` → `reasoning-ended` →
  `output-detected` → `lid-play`。

浏览器里跑的时候，页面会把真实 `<video>` 状态与每列 alpha 覆盖量
POST 回 `/report`，由预览服务器打到自己的 stdout —— 因为无头浏览器的 stdout
调用方拿不到。截图里那行 `PROBE` 就是同一份数据写回 DOM 的结果；
`?idle=1` 那套还会把一条**时间线**放进 `window.__timeline`（每 50ms 采样一次，
只在"画面换人"时记一笔，附累计起播次数），并把"屏幕上到底有几段画面"的越界
记进 `window.__violations`、把"退回开场定格帧"的次数记进 `window.__fallsBack`
（判据是真实 `style.visibility`，不是挂件自己的账本）。
拿 `test/cdp-eval.mjs` 取回来的实测记录：

```text

t=12.3s  idle       ← 拆完后的第一拍（idleEvery 5s）
t=17.5s  idle(holding)  ← 播完停在它自己的末帧（0.5.1 及以前这里是 frozen）
t=22.4s  idle       ← 第二拍
t=27.6s  idle(holding)
t=32.4s  idle       ← 第三拍
t=37.6s  idle(holding)
t=42.4s  idle       ← 第四拍
t=47.7s  idle(holding)
t=52.4s  act        ← 动作那一拍（与 idle 的第 8 拍同时到点 → 动作优先）
```

每一段都完整播完，**任何时刻都只有一段画面**（`violations` 为空），
**并且一次都没有退回开场定格帧**（`fallsBack` 为空 —— 0.6.0 起空档期留在
上一段的末帧上，所以时间线里是 `idle(holding)` 而不是 `frozen`）；
`idle` 与 `act` 的起播次数比例也正好是 5 秒与 15 秒该有的样子。

`?sched=1` 那条专门验暂停 / 继续（脚本在 1s / 4s / 13s / 16s 各点一次按钮），
实测时间线：

```text

t=16.4s  idle(paused)    ← 暂停：画面原样冻住，仍是这一段
t=19.4s  idle(holding)   ← 继续：排期的位放开，但画面不撤（0.5.1 及以前这里是 frozen）
t=24.4s  idle(playing)   ← 节拍照常起播（0.5.1 之前这里再也不会动）
t=25.2s  idle(holding)   ← 再暂停一次
t=25.4s  idle(holding)   ← 再继续
t=36.5s  idle(playing)   ← 继续照常
t=46.5s  act(playing)    ← 动作那一拍也照常轮到

one-picture violations = 0    fell back to the opener frame = 0    plays idle=3 act=1
```

全程 `one-picture violations = 0`：每一次采样，屏幕上恰好是一段画面。

用无头 Chromium 抓图（`docs/` 下两张截图就是这么来的）：

```powershell
msedge --headless=new --disable-gpu --window-size=1280,800 `
  --user-data-dir="$env:TEMP\dshca" --virtual-time-budget=25000 `
  --screenshot=out.png "http://127.0.0.1:19399/?drag=1"
```

> 注意：`--virtual-time-budget` **不会推进媒体播放**（虚拟时间跑完了，视频才播了 1 秒）。
> 预览页因此挂了一个 `/slow` 延迟资源把 `load` 事件拖住 9 秒，截图才会落在
> 动画真正播完之后 —— 否则你抓到的永远是中间某一帧。

### 0.10.0 那三件事的自检（`?random=1` 与 `test/cdp-random.mjs`）

三道随机动画靠手点根本复现不了，所以 0.10.0 的自检是**脚本驱动的**：

```powershell
node test/preview-server.mjs 19399
node test/cdp-random.mjs http://127.0.0.1:19399/ docs/dev-checks all
#   all（默认）| roll | lid1 | lid2 | drag
```

`?random=1` 是同一套检查的"人肉版"（不用起 CDP 脚本，打开就能看，结果 POST 回
预览服务器的 stdout）。它按顺序验：

1. **概率分布**：走真实的点击路径掷 400 次，统计 A / B / 都没中 的占比，
   并且每次掷中立刻收工 —— 断言落在 `20% ±` 与 `10% ±` 的合理带里
   （实测 `18.3~24.0%` / `6.0~10.0%`），同时**没有任何一次同时出现两口锅**；
2. **动画1**：起播 → 看到它自己走到末帧 → **看到时间轴真的在往回走**（倒放的证据）
   → 收工后 `currentTime` 回到 **0**、画面交回定格图、没有残留的 `transform`；
3. **动画2**：起播 → 采样 `fly` 的位移（证明它真的在移动）→ 采样接触时的重叠率
   （实测 0.503，正好越过 50% 那条线）→ 收工后断言**电饭煲回到原位**
   （`left`/`top` 与动画前逐像素相同）、**小女孩那一块没被动过**、
   `transform` 与 `dshca-flying` 都清掉了、**两条节拍重新在跑**；
4. **拖动动画**：起播后循环（5.6 秒后 `currentTime` 仍在走、没有 `ended`）、
   她那格定格图让位、松手后 `display:none` + 她的定格图回来 + 位置不变；
   另外还**真的合成一次 pointer 拖动**，断言拖动期间这一段确实出画了；
5. **不变量**：整轮每 60ms 采样一次"两侧各有几段画面"，
   违规必须为 **0**（0.10.0 开发过程中它抓到过三次真实的"闪一下不见了"，
   见上面「顺手修掉的三处老毛病」）。

留痕截图：`docs/dev-checks/v010-{initial,lid1-playing,lid1-reversing,lid1-back,lid2-start,lid2-moving,lid2-back,drag-on,drag-off}.png`。
>
> 想拿到「首次打开、两块还贴在一起」的样子，记得用一个**全新的
> `--user-data-dir`**：两块的位置也记在 `localStorage` 里，沿用旧配置会看到
> 上次拖开的位置。
>
> 更可靠的做法是走 CDP 而不是 `--screenshot`：`--virtual-time-budget` 只推进
> 渲染进程里的计时器，媒体加载在别的进程里按真实时间走，于是 `<video>` 永远
> 等不到 `loadedmetadata`；`--screenshot` 又会在 `load` 之后立刻拍。
> 预览页为此暴露了 `window.__ready`：等它变 true 再截图即可。

```powershell
# 等页面自己报告「这批诊断已经跑完」再抓图
node test/cdp-shot.mjs "http://127.0.0.1:19399/?drag=1" out.png "window.__ready" 90 1500
```

`test/cdp-shot.mjs` 的参数依次是「页面 URL / 输出 PNG / 等待表达式 / 超时秒数 / 静置毫秒」，
它会开 `--remote-debugging-port`，用 Node 内置 WebSocket 客户端轮询表达式，
成立之后再 `Page.captureScreenshot`，并把页面上的 `window.__result`、`window.__report`
一起打印出来 —— 无头浏览器的 stdout 是取不回来的，这是唯一能把结果带出来的通道。
`docs/dev-checks/` 下的图就是用它抓的（细节见那里的 README）。

要看**随时间变化**的东西（比如两条节拍），用同一套机制取回 JSON 更合适：

```powershell
# 等到动作动画已经轮到过、且待机至少起播两次，然后把时间线取回来
node test/cdp-eval.mjs "http://127.0.0.1:19399/?idle=1" `
  "window.__clipPlays.act >= 1 && window.__clipPlays.idle >= 2" 60 `
  "JSON.stringify({plays: window.__clipPlays, timeline: window.__timeline}, null, 1)"
```

`test/cdp-eval.mjs` 的参数依次是「页面 URL / 等待表达式 / 超时秒数 / 结果表达式」，
结果表达式缺省取 `window.__result || window.__report`。上面那段 README 里的
实测时间线就是这么跑出来的。

## 边界

- 不读取、不保存任何凭据；不联网；不发遥测。
- 只监听自己的 7 条命名路由（`widget.js` / `anim.webm` / `idle.webm` / `act.webm` /
  `girl.webm` / `lid.webm` / `status`），全部静态只读。
- 只操作自己创建的那棵 DOM 子树，不触碰 DSH 的 React 树。0.7.0 的发送联动会**读**
  页面上其他元素的文案与文本长度（用来判断"点没点发送"和"有没有开始输出"），
  但从不修改它们、也不往里插任何东西。
- 全部持久化只有六个 `localStorage` 键：
  `dsh-corner-anim:pos:v1`（整体位置）、`dsh-corner-anim:pos:cooker:v1` 与
  `dsh-corner-anim:pos:girl:v1`（拆分后两块的位置）、`dsh-corner-anim:size:v1`（大小）、
  `dsh-corner-anim:speed:v1`（动画间隔倍率）、
  `dsh-corner-anim:panel:v1`（面板展开状态）。两段动画本身都不写任何状态。
- **几乎全程静音**：主素材自带 Vorbis 音轨但元素始终 `muted`；`idle` / `act` / `girl`
  三份素材都没有音轨（`idle` 那份在打包前抽掉了，另两份本身就是无声的）。
  唯一会出声的是 `lid.webm` —— 按用户要求保留了原始音轨，并且只可能在
  "用户点过发送之后"才会响；不想要就把 `sendLidAudio` 设成 `false`。
